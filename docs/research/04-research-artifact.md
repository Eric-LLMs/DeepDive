# 04 — ResearchArtifact Contract

> **Normative.** Supersedes `02-domain-model.md` §2.2 where more specific.

## 1. Artifact is a domain object, not a file abstraction

An artifact is a versioned record of a research product (corpus, design, dataset, table,
result, evidence, manuscript, ...) with lineage. Its bytes live either in **scratch** or in
the **cloud drive**; the record lives in `research_artifacts` and (when relevant) the graph.

## 2. Versioning model

- `artifact_id` is stable across versions. `(artifact_id, version)` is unique.
- `version` starts at 1 and increments monotonically; it is **immutable once written**.
- `parent_version` records derivation (v3 ← v2 ← v1).
- A `FROZEN` version is read-only. Any change to frozen content creates a **new version**
  with `parent_version` set to the frozen one. There is no in-place edit of frozen content.

## 3. Status lifecycle

```text
DRAFT ──▶ VALIDATED ──▶ PROMOTED ──▶ FROZEN ──▶ SUPERSEDED
  │            │             │            │
  └────────────┴─────────────┴────────────┴──▶ INVALID
```

| Status | Meaning | Entered by |
|---|---|---|
| `DRAFT` | Working content in scratch, not yet validated | `write_scratch` |
| `VALIDATED` | Passed an internal check (evidence gate, mechanical check) | gate machinery |
| `PROMOTED` | Promoted to the cloud drive (durable Source of Record) | `promote_to_drive` |
| `FROZEN` | Released milestone; read-only | gate PASS on the owning stage |
| `SUPERSEDED` | A newer version exists (old version demoted) | `create_version` |
| `INVALID` | Upstream invalidated the artifact's lineage | `invalidate_downstream` |

Only `PROMOTED`/`FROZEN` artifacts live in the drive. `DRAFT`/`VALIDATED`/`SUPERSEDED`/
`INVALID` may live in scratch.

## 4. Storage mapping

| `storage_scope` | Location | Management |
|---|---|---|
| `scratch` | `{research_scratch_dir}/{owner_id}/{project_id}/{storage_path}` | ephemeral; purgeable; never the basis for a claim |
| `drive` | cloud-drive folder `research/{project_id}/{storage_path}` via `DriveService.save_artifact(user_id, name, mime_type, content, folder_path="research/<project_id>")` | durable, deduped, ref-counted, shareable |

Rules:

- Promotion is **one-way** (scratch → drive). Never sync drive content back into scratch as
  an authoritative copy.
- `save_artifact` already dedupes by SHA-256 and auto-uniques names; `storage_path` in the
  artifact record is the **logical** path, independent of the physical asset name.
- Drive promotion for text/code/data assets may trigger the existing RAG ingest so the
  artifact becomes searchable (see `14`). RAG is derived; it never writes back.

## 5. Checksum and provenance

- `checksum` is the SHA-256 hex of the promoted content; computed at write, verified at
  promotion.
- `generated_by_execution` links the artifact to the immutable `ResearchExecution` that
  produced it.
- **Producer invariant**: an artifact generated by an Agent / Sub-Agent / Skill execution
  **must** have a non-null `generated_by_execution` (`execution_id`). A user-authored intake
  file or a user-uploaded raw file **must allow** `generated_by_execution == null` but
  **must** carry a non-null `created_by` (`user_id`).
- `derived_from[]` and `supports_claims[]` are denormalized mirrors of graph edges
  (`derived_from`, `supports`) for fast reads; the graph is authoritative.

## 6. Idempotency

- Writers supply `idempotency_key` (e.g. `execution_id:artifact_type:step`).
- A write with an existing `(project_id, idempotency_key)` returns the existing artifact
  instead of creating a duplicate. This prevents duplicate files after retries.
- Colliding keys with different content raise a conflict error (never silent overwrite).

## 7. `write_scratch` / `promote_to_drive` / `create_version` / `diff`

| Action | Effect |
|---|---|
| `write_scratch(path, content, idempotency_key)` | Write bytes under scratch; create/update DRAFT artifact row; compute checksum |
| `promote_to_drive(artifact_id, version, meta)` | Copy scratch bytes → drive via `save_artifact`; set `PROMOTED`, `storage_scope=drive`; record `storage_path`; optionally enqueue RAG ingest |
| `create_version(artifact_id, content)` | Freeze current (→ `FROZEN` unless already), demote older to `SUPERSEDED`, mint `version+1` with `parent_version` |
| `diff(artifact_id, v1, v2)` | Compare content or metadata between two versions |

## 8. Lifecycle invariants

1. No artifact row without a project, a checksum, and a producer.
2. `FROZEN` content is byte-immutable.
3. `PROMOTED` implies the bytes exist in the drive (verified by `save_artifact` return).
4. Deleting a drive asset must not silently remove the artifact record — the record is
   marked `INVALID`/`SUPERSEDED` and the drive deletion is a separate, human-audited action.
5. Execution-produced artifacts have non-null `generated_by_execution`; user-intake files
   have non-null `created_by` and `generated_by_execution == null`.
